## 二、基础设施准备

### 2.1 数据服务清单

| 服务 | 容器名 | 镜像 | 端口映射 | 关键配置 |
| --- | --- | --- | --- | --- |
| MySQL 8 | `agri-mysql`（可复用 `datasec-mysql`） | `mysql:8.0` | 13306→3306 | 库 `agri_price`、账号 `agri` / `Agri_2026`、`utf8mb4`、时区 +08:00 |
| Redis 7 | `agri-redis`（可复用 `datasec-redis`） | `redis:7-alpine` | 16379→6379 | 密码 `DataSec_2026`、AOF 开启 |
| MinIO | `agri-minio` | `minio/minio:latest` | 9000→9000、9001→9001 | 账号 `agri` / `Agri_2026_minio`、桶 `agri-artifacts` |
| Mailpit | `agri-mailpit` | `axllent/mailpit:latest` | 1025→1025、8025→8025 | 允许无认证登录、最多保留 500 封 |

### 2.2 `npm run infra:up` 的行为

执行 `node scripts/infra.mjs`，逐项检查并幂等准备，最后输出统一结果行 `RESULT=PASS passed=N failed=M 用时=Ss`：

1. 检查 Docker 服务可用（`docker version`）。
2. MySQL / Redis：容器已存在则启动（若停止），不存在则报错并提示用 compose 拉起；等待端口就绪。
3. MinIO：优先复用或通过 compose 启动容器；镜像不可达时自动下载官方服务端二进制到 `.runtime/minio/minio.exe`，数据目录 `.runtime/minio/data`，对外仍为 9000/9001 的 S3 接口。
4. Mailpit：容器未运行时由 compose 拉起，等待 8025 可访问。
5. 业务库与账号：`CREATE DATABASE IF NOT EXISTS`、`CREATE USER IF NOT EXISTS`、`ALTER USER`、`GRANT`，重复执行结果一致。
6. 应用侧连通性探针：SQLAlchemy 连接数据库并 `SELECT 1`、redis-py `PING` 读取版本、MinIO 建桶并写入 `health/probe.txt`、SMTP `NOOP` 探测。
7. 附加检查：MinIO 控制台 9001 可访问、Mailpit 8025 收件箱可访问。

幂等语义：全部步骤为「存在即跳过、缺失即创建、权限以最新配置为准」，可在任意时刻重复执行，不会清空业务数据。容器名可用环境变量覆盖（`AGRI_MYSQL_CONTAINER`、`AGRI_REDIS_CONTAINER`、`AGRI_MINIO_CONTAINER`、`AGRI_MAILPIT_CONTAINER`）。

### 2.3 手工准备（可选）

```bash
# 通过编排启动四个数据服务
docker compose -f deploy/docker-compose.yml up -d
# 查看健康状态
docker ps --filter "name=agri-" --format "{{.Names}}  {{.Status}}"
# 停止由编排启动的服务（不删除数据卷）
npm run infra:down
```

无 Docker 时可使用回退路径：`AGRI_DB_BACKEND=sqlite` 退化为 `.runtime/agri.db` 单文件库；MinIO 不可用时对象存储降级到 `.runtime/storage/`；Redis 不可用时缓存与限流自动降级（见第五章）。

## 三、安装步骤

### 3.1 六步安装

| 步骤 | 命令 | 预期结果 | 耗时 |
| --- | --- | --- | --- |
| 1. 获取代码 | 解压源码包或在仓库目录执行 `git clone` | 项目根目录含 `package.json`、`backend/`、`frontend/` | 分钟级 |
| 2. 安装 Python 依赖 | `python -m venv .venv` 后执行 `.venv\Scripts\python -m pip install -r backend/requirements.txt` | Python 运行环境目录 `.venv` 生成，FastAPI/SQLAlchemy/pandas/scikit-learn 等安装完成 | 3～5 分钟 |
| 3. 安装前端依赖 | `npm ci`（根目录）与 `npm ci --prefix frontend` | `node_modules` 与 `frontend/node_modules` 就绪 | 2～5 分钟 |
| 4. 生成种子数据 | `npm run infra:up` 后执行 `npm run seed` | 重建库并输出价格、特征、模型等统计；约 126 秒（含 120 个模型训练） | 约 2 分钟 |
| 5. 前端生产构建 | `npm run build` | 类型检查通过，产物输出 `frontend/dist` | 1～2 分钟 |
| 6. 启动服务 | `npm run dev`（开发）或生产启动后端 | 后端 8017 健康检查通过，前端 5177 可访问 | 30～60 秒 |

### 3.2 种子数据说明

- `npm run seed` 等价于 `python -m app.seed --reset`：清空业务数据后按固定随机种子重放，结果可复现。
- 生成规模：价格记录 84,660 条（60 个序列 × 1,411 天，2023-01-01～2026-11-11）、特征记录 31,380 条、5 个品种、6 个地区、12 个市场、5 个数据源、120 个模型版本（30 组在用）、120 条模型实验记录、6 条预警规则与 6 条预警记录、3 份报告、48 条质量问题、3 条导入任务、10 条调度运行史、19 条站内通知、3 个开放 API 调用方与 237 条流水、5 条邮件记录、18 条审计日志。
- 快速建库：`npm run seed -- --no-models` 跳过模型训练，适合仅验证接口与页面。
- 注意：重建会清空业务表，生产环境执行前必须先备份并停止后端，避免运行期写入冲突。

### 3.3 生产启动

```bash
cd backend
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8017
```

若已执行 `npm run build`，后端会自动挂载 `frontend/dist` 并在 8017 提供 SPA 页面与静态资源，无需单独部署前端服务；未构建时访问根路径返回 404，接口不受影响。

## 五、启动、停止与端口排查

### 5.1 前台启动

```bash
npm run dev
```

脚本 `scripts/dev.mjs` 先以 `--reload` 启动后端 8017（日志写入 `.runtime/logs/backend-dev.log`），健康检查通过后启动前端 5177；`Ctrl+C` 会同时终止两个子进程。首次启动需等待建表与初始化，约 30～60 秒。

### 5.2 后台运行

生产与验收环境建议直接托管后端进程（Windows 计划任务或 NSSM 注册为服务），示例：

```powershell
cd D:\MyCodes\agri-price-platform\backend
Start-Process -FilePath "..\.venv\Scripts\python.exe" `
  -ArgumentList "-m","uvicorn","app.main:app","--host","127.0.0.1","--port","8017" `
  -WindowStyle Hidden -RedirectStandardOutput "..\.runtime\logs\uvicorn.out.log" `
  -RedirectStandardError "..\.runtime\logs\uvicorn.err.log"
```

### 5.3 端口占用排查

```powershell
# 查看 8017 占用进程
Get-NetTCPConnection -LocalPort 8017 -State Listen | Select-Object LocalPort,OwningProcess
# 按 PID 查进程名
Get-Process -Id <OwningProcess>
# 终止占用进程（确认 PID 属于本项目后再执行）
taskkill /PID <OwningProcess> /F
# 连续释放多个端口
foreach ($p in 8017,5177) { Get-NetTCPConnection -LocalPort $p -State Listen -ErrorAction SilentlyContinue | ForEach-Object { taskkill /PID $_.OwningProcess /F } }
```

停止数据服务：`npm run infra:down`（仅停止编排容器，保留数据卷）；若使用复用的 `datasec-mysql` / `datasec-redis` 容器，应通过 `docker stop` 单独控制，避免影响同机其他系统。

## 六、备份与恢复

### 6.1 备份

```bash
npm run backup
```

脚本 `scripts/backup.mjs`（带 `--keep`）执行四步（方案记录于 `DECISIONS.md` D27）：

1. `docker exec datasec-mysql mysqldump -uroot --single-transaction --no-tablespaces --quick --default-character-set=utf8mb4 agri_price`，导出结构与数据；小于 64 KB 视为失败。
2. 统计关键表行数（价格、特征、模型版本、模型实验、预测结果、预警、预警规则、报告、调度任务、调度运行史、通知、邮件、调用流水、审计、用户），写入 `<库名>-<时间戳>-manifest.json`。
3. 导出对象存储清单（MinIO 对象或本地 `fs` 目录）为 `<库名>-<时间戳>-objects.json`，单文件最多记录 500 个对象。
4. 校验文件落盘并按时间戳保留最近 7 份，超出的 sql/manifest/objects 一并清理。

建议：生产环境每日凌晨执行一次；重大升级、重建种子、批量删改数据前手工执行一次。

### 6.2 恢复演练

| 步骤 | 操作 | 校验点 |
| --- | --- | --- |
| 1 | 停止后端，确认无写入 | `Get-NetTCPConnection -LocalPort 8017` 无监听 |
| 2 | 在 MySQL 创建临时库 `agri_price_restore` | `SHOW DATABASES` 可见 |
| 3 | 导入：`docker exec -i datasec-mysql mysql -uroot -p agri_price_restore < .runtime/backups/agri_price-<时间戳>.sql` | 无报错退出码 0 |
| 4 | 行数核对：对照 manifest 中各关键表计数逐表 `SELECT COUNT(*)` | 与 manifest 完全一致 |
| 5 | 对象核对：对照 objects.json 抽查报告/模型产物可下载 | 文件存在且大小一致 |
| 6 | 切换验证：将临时库改名为 `agri_price` 或修改 `AGRI_DATABASE_URL` 指向临时库后启动 | `/api/health` 中 `db=ok`，登录与驾驶舱可用 |

演练完成后删除临时库与临时环境变量，恢复正式连接串。重要提示：恢复前先备份当前库，避免二次损失。

## 七、监控与巡检

### 7.1 健康检查四态

`GET /api/health` 无需登录，返回 `status`、`version`、`db`、`cache`、`storage`、`storage_backend`、`scheduler`、`mail`、`uptime_seconds`：

| 字段 | 取值 | 含义 | 处置建议 |
| --- | --- | --- | --- |
| `db` | `ok` / `error` | MySQL 可执行 `SELECT 1` | `error` 时检查容器、端口 13306、账号口令 |
| `cache` | `ok` / `error` | Redis `PING` 成功 | `error` 时缓存降级直连，按第五章排查 Redis |
| `storage` | `ok` / `degraded` | MinIO 可用且未降级 | `degraded` 时对象落本地 `.runtime/storage`，见 8.3 |
| `scheduler` | `ok` / `paused` | 进程内调度器运行中 | `paused` 表示 `AGRI_SCHEDULER=0` 或启动失败 |
| `mail` | `ok` / `paused` | 邮件通道开启 | `paused` 表示 `AGRI_MAIL_ENABLED=0` |

`status` 在数据库可用时为 `ok`，数据库不可用时为 `degraded`；`uptime_seconds` 用于确认进程是否发生过重启。

### 7.2 运行指标与日志

| 入口 | 权限 | 用途 |
| --- | --- | --- |
| `GET /api/system/status` | 登录 | 聚合 db/cache/storage/scheduler/mail/logs/metrics 与运行时长，页面「系统监控」同源 |
| `GET /api/metrics/summary?minutes=60` | `admin:task` | QPS、平均/分位耗时、错误率、缓存命中率、慢接口 TOP |
| `GET /api/metrics/timeseries?minutes=60` | `admin:task` | 分钟级 QPS/耗时/错误率曲线，缺失分钟补零 |
| `GET /api/logs?limit=100&level=&module=&keyword=` | `admin:audit` | 检索 `.runtime/logs/app.jsonl`，含请求 ID 与缓存状态 |
| `GET /api/tasks/runs` | `admin:task` | 调度任务运行史（成功/失败、耗时、触发方式） |
| `GET /api/storage/health` | `admin:task` | 存储后端、桶、降级原因与对象数 |

日志轮转：单文件达到 8 MB 自动滚动为 `app.jsonl.1`…`app.jsonl.3`，保留 3 份，总占用上限约 32 MB；滚动与写入异常只影响日志本身，不影响业务。

### 7.3 巡检清单

| 频次 | 检查项 |
| --- | --- |
| 每日 | `/api/health` 五项状态、磁盘剩余空间、`.runtime/backups` 是否生成当日备份 |

## 八、故障处理

### 8.1 常见故障对照表

| 现象 | 可能原因 | 定位命令/接口 | 处理步骤 |
| --- | --- | --- | --- |
| 接口大面积 500，`/api/health` 中 `db=error` | MySQL 容器停止、端口被占、账号口令错误 | `docker ps --filter name=mysql`；`Test-NetConnection 127.0.0.1 -Port 13306` | 启动容器或改端口映射；核对 `AGRI_MYSQL_*`；执行 `npm run infra:up` |
| `cache=error`，日志出现「Redis 缓存不可用，已降级为直连数据库」 | Redis 停止、密码错误、连接超时 | `docker exec datasec-redis redis-cli -a DataSec_2026 ping` | 业务不中断，接口变慢；启动容器或修正 `AGRI_REDIS_URL` 后自动恢复，无需重启 |
| `storage=degraded`，`error` 提示 MinIO 客户端异常 | MinIO 未启动、桶不可用、客户端参数不兼容 | `GET /api/storage/health`；`http://127.0.0.1:9000/minio/health/live` | 启动 MinIO（容器或 `.runtime/minio/minio.exe`）；对象自动落本地目录，恢复后新对象回 S3 |
| 邮件不达，`POST /api/mail/test` 返回 `sent=false` | Mailpit 未启动、端口 1025 被占 | `http://127.0.0.1:8025/api/v1/messages`；`Test-NetConnection 127.0.0.1 -Port 1025` | 启动 `agri-mailpit` 容器；失败原因已写入 `sys_email_log`，不影响主流程 |
| 前端页面 404 或空白 | 未执行 `npm run build`，`frontend/dist` 不存在 | 检查 `frontend/dist/index.html` | 执行 `npm run build` 后重启后端；开发模式用 5177 |
| 访问不存在或拼写错误的 `/api/路径` 返回 404 `E4040` | 路由不存在或前端代理未指向 8017 | 对照 `docs/接口契约*.md`；检查 Vite 代理配置 | 核对路径与方法；修正代理后重启前端 |
| 登录返回 401 `E4010` | 口令错误、账号停用、令牌过期、令牌已注销 | 查看登录响应与审计记录 | 重新登录；管理员确认账号状态；令牌过期属正常现象 |
| 接口返回 429 `E4290` | 开放 API 调用方超过每分钟限额 | 响应头 `Retry-After`；`GET /api/open-clients/{id}/usage` | 降低调用频率或在调用方列表调高 `rate_limit` |
| `npm run gate` 某道门禁失败 | 构建、数据库、接口、端到端或文档断言不通过 | 查看失败项与最后一行 `RESULT=FAIL passed=N failed=M` | 按失败项修复后单跑对应脚本（`npm run db:validate`、`npm run test:api` 等），通过后再跑总门禁 |
| 种子重建失败 | 数据库被占用、容器未就绪、磁盘不足 | `npm run infra:up`、`npm run db:validate` | 停止后端、确认容器健康、清理磁盘后重试 |

### 8.2 典型场景处理

- MySQL 主备切换/迁移：先停后端，`npm run backup` 导出，导入目标库，修改 `AGRI_DATABASE_URL` 后启动，最后用 `npm run db:validate` 校验表结构与数据规模。
- Redis 内存告警：缓存键均有 TTL（30～300 秒），可临时 `AGRI_CACHE_ENABLED=0` 关闭缓存缓解；确认无大量无 TTL 键后再扩容。
- 日志快速膨胀：检查是否有循环报错或 `request.exception`，修复根因；必要时调小 `AGRI_LOG_MAX_BYTES` 或降低访问日志量。
- 备份文件过大：mysqldump 已使用 `--quick` 流式导出；可在低峰期执行并确保备份目录所在磁盘余量大于库大小的 2 倍。

## 九、升级与回滚

### 9.1 升级步骤

| 步骤 | 操作 | 说明 |
| --- | --- | --- |
| 1 | 停止后端与前端进程 | 避免升级期间写入 |
| 2 | 执行 `npm run backup` 并确认产物 | 记录 manifest 行数，作为回滚依据 |
| 3 | 更新时间戳与版本号 | `backend/app/config.py` 的 `APP_VERSION`；`package.json` 版本号 |
| 4 | 替换代码、安装新依赖 | `pip install -r backend/requirements.txt`、`npm ci`（根与 frontend） |
| 5 | 启动后端执行自动建表与初始化 | `Base.metadata.create_all` + `ensure_initialized`，新增表自动创建、不删旧表 |
| 6 | 重建或迁移数据 | 结构变更按 `backend/app/seed.py` 中的迁移函数执行；必要时 `npm run seed` 重建 |
| 7 | 构建前端并验证 | `npm run build`，打开 5177/8017 关键页面 |
| 8 | 回归门禁 | `npm run gate`，五道门禁全部 PASS 后交付 |

### 9.2 回滚步骤

1. 停止后端进程，确认 8017 无监听。
2. 用升级前的备份恢复数据库（见第六章恢复演练），或直接 `mysql < agri_price-<时间戳>.sql` 覆盖回滚。
3. 切换代码到上一版本标签/目录，重新安装依赖（依赖未变可跳过）。
4. 启动后端，检查 `/api/health` 五项状态与 `npm run db:validate`。
5. 如升级涉及对象存储结构，按 `objects.json` 恢复对应报告/模型产物。

### 9.3 版本标记建议

| 标记位置 | 内容 | 用途 |
| --- | --- | --- |
| `backend/app/config.py` | `APP_VERSION = "1.0.0"` | `/api/health` 与 Swagger 展示运行版本 |
| `package.json` | `version` | 源码包与构建产物版本 |
| `.runtime/backups/` 文件名 | 时间戳（到分钟） | 与升级记录一一对应 |
| 审计日志 | 升级前后各一次登录记录 | 证明升级窗口内无越权操作 |
