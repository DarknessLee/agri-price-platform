# 安全与合规说明

> 文档目的：说明本系统在身份认证、访问控制、审计追溯、传输与存储、数据安全、开放接口六个方面的安全设计与实测结论，并如实列示与等级保护基本要求之间的差距及整改计划。
> 适用读者：项目评审与验收人员、信息系统安全管理员、运维负责人。
> 对应交付物：开发书 §12 第 08 项《安全与合规说明》。
> 编写基线：与同一套代码、同一份种子数据对应，数字来源见 `deliverables/00-交付物清单.md`；引用位置均为仓库相对路径。

## 二、身份认证

认证与授权方案记录于 `DECISIONS.md` D06：采用自实现 HS256 JWT 与 PBKDF2 口令散列，RBAC 以「角色—权限点」映射实现，权限点同时驱动后端接口校验与前端菜单/按钮显隐。

### 2.1 账号体系

系统内置 7 个账号，覆盖 4 类角色，口令首次由 `backend/app/seed.py:154-162` 的 `USERS` 常量写入，落库前统一经 `hash_password()` 生成散列，任何接口与日志都不出现明文口令。

| 账号 | 角色 | 权限点数量 | 说明 |
| --- | --- | --- | --- |
| `admin` | 系统管理员 | 21 | 平台全量权限，负责账号、角色、基础数据与运维 |
| `analyst01` / `analyst02` | 价格分析师 | 12 | 监测导出、预测执行、模型管理、情景、报告生成 |
| `operator01` / `operator02` | 监测员 | 10 | 监测、预警处置与规则、报告查看、数据导入 |
| `viewer01` / `viewer02` | 领导/访客 | 6 | 只读：驾驶舱、监测、预测、预警、报告、情景 |

### 2.2 口令存储

- 算法：PBKDF2-HMAC-SHA256，迭代 120,000 轮，盐为 16 字节随机数（`os.urandom(16)`）。
- 存储格式：`pbkdf2_sha256$120000$<salt-hex>$<digest-hex>`，散列比对使用 `hmac.compare_digest`，抵御时序侧信道。
- 代码位置：`backend/app/security.py:39-51`（`hash_password` / `verify_password`）。
- 口令自服务修改：`PUT /api/auth/password`，需同时提交原口令，新口令长度不少于 8 位，修改成功写审计（`backend/app/routers/auth.py:87-96`）。
- 管理员重置：`PUT /api/users/{user_id}/password` 由 `admin:user` 权限调用，重置动作写审计（`backend/app/routers/admin.py:270-280`）。
- 强度策略：当前校验为最小长度 8 位（`PASSWORD_MIN_LENGTH = 8`，`backend/app/routers/admin.py:34`）；未强制大小写、数字、符号组合，属已知差距（见第七章）。

### 2.3 登录失败处理

- 账号不存在与口令错误返回同一文案「用户名或密码不正确」，避免账号枚举（`backend/app/routers/auth.py:58-59`）。
- 停用账号返回「账号已停用，请联系管理员」（`backend/app/routers/auth.py:60-61`）。
- 登录成功更新 `last_login_at` 并写「登录」审计，记录账号、IP 与时间。
- 未实现连续失败锁定与验证码，属已知差距（见第七章第 3 项，已纳入整改计划）。

### 2.4 JWT 令牌

| 项目 | 设计 |
| --- | --- |
| 算法 | HS256，密钥取自 `AGRI_SECRET_KEY`（`backend/app/config.py:64`） |
| 载荷 | `sub`（用户 ID）、`username`、`role`、`iss`、`iat`、`exp`、`jti` |
| 有效期 | 720 分钟（`AGRI_TOKEN_EXPIRE_MINUTES`，登录响应同步返回 `expires_in`） |
| 签名校验 | 服务端重算 HMAC 后 `hmac.compare_digest` 比对；失败统一 `E4010` |
| 过期校验 | `exp` 小于当前时间返回「登录已过期，请重新登录」 |
| 会话区分 | 每次登录生成 8 字节随机 `jti`，同一秒多次登录不会产生相同令牌，注销时按令牌指纹精确失效，不影响其他会话 |

### 2.5 令牌黑名单与即时失效

- 注销：`POST /api/auth/logout` 调用 `revoke_token()`，把令牌的 SHA-256 十六进制指纹写入 Redis 键 `agri:jwt:blacklist:<sha256>`，TTL 等于令牌剩余有效期（`backend/app/security.py:126-132` 的 `revoke_token()`，`:109-118` 的 `blacklist_token()`）。
- 校验：`get_current_user()` 在签名、过期校验之后查询该键，命中则抛出 `ApiError("E4010", "登录凭证已失效", 401)`（`backend/app/security.py:146-157`）。
- 降级：Redis 不可用时 `exists()` 返回 False，按「放行」处理并在健康检查中暴露 `cache=error`；这是可用性优先的明确取舍，记录在 `DECISIONS.md` D13。
- 实测结论（2026-11-12，后端 8018）：登录取得令牌 → 注销返回 200 → 用旧令牌访问 `GET /api/auth/me` 返回 HTTP 401、`{"code":"E4010","message":"登录凭证已失效"}`；Redis 中 `agri:jwt:blacklist:<64 位十六进制>` 的 TTL 实测 43,194 秒，与 12 小时有效期扣除已用时长一致。
- 键空间隔离：缓存、限流、黑名单分别使用 `agri:<domain>:*`、`agri:openapi:rate:*`、`agri:jwt:blacklist:*` 前缀，互不覆盖。

### 3.3 接口级校验

所有业务端点通过 `Depends(require_permission("<权限点>"))` 声明所需权限，`_checker` 从 `role_permission` 实时读取角色权限集合，取交集为空即抛出 `ApiError("E4030", "当前账号无权执行该操作", 403)`（`backend/app/security.py:168-177`）。读写分离：查看类接口要求 `*:view`，执行类接口要求 `*:run`/`*:handle`/`*:generate`/`*:manage`，避免「可看即可改」。

### 3.4 前端双重过滤

- 路由层：每条路由声明 `meta.permission`，`router.beforeEach` 在登录态校验之后比对当前用户权限，不满足则跳转 `/forbidden`（`frontend/src/router/index.ts:170-190`）。
- 菜单层：菜单树由 `GET /api/meta/menus` 按服务端权限过滤后返回，只渲染可访问入口；菜单树不进入缓存，避免跨用户串权。

## 五、传输与存储安全

### 5.1 传输边界

- 当前交付形态为内网单机 HTTP：后端 `127.0.0.1:8017`、前端开发服务 `5177`，CORS 白名单限定 `127.0.0.1:5177`、`localhost:5177`、`127.0.0.1:4177`（`backend/app/main.py:47-53`）。
- 令牌通过 `Authorization: Bearer` 头传递，不放在 URL 查询串，避免进入访问日志与浏览器历史。
- 生产化部署建议：前置 Nginx/Caddy 反向代理终结 TLS（443 → 8017），启用 HSTS、仅允许 TLS 1.2+；代理层透传 `X-Forwarded-For` 后，审计 IP 即为真实客户端地址。该事项为整改计划第 1 项。

### 5.2 数据服务凭据与可达范围

| 服务 | 端口 | 账号/口令 | 可达范围与加固现状 |
| --- | --- | --- | --- |
| MySQL 8 | 13306 | `agri` / `Agri_2026` | 仅授予 `agri_price` 库权限；容器端口映射到本机回环，不对外网暴露 |
| Redis 7 | 16379 | 密码 `DataSec_2026` | 开启 AOF；仅存缓存、限流计数与令牌指纹，不存业务明文 |
| MinIO | 9000/9001 | `agri` / `Agri_2026_minio` | 桶 `agri-artifacts` 由应用创建，未配置匿名读写策略，默认私有 |
| Mailpit | 1025/8025 | 无认证（本地收件箱） | 仅供本地验证，禁止部署到对外网段 |

口令均支持环境变量覆盖，生产部署应替换默认值并纳入密钥管理（整改计划第 5 项）。对象存储的桶策略、生命周期与访问密钥轮换应在 MinIO 控制台按部署单位的存储规范配置；备份文件 `.runtime/backups/*.sql` 为明文导出，建议落盘前加密并限制目录 ACL。

### 5.3 缓存层的安全约束

- 只缓存与用户权限无关的聚合结果：驾驶舱四类统计、字典、价格序列、模型性能；菜单树按用户权限过滤，严禁整体缓存（`backend/app/routers/meta.py`）。
- 缓存键为 `agri:<域>:<参数 SHA-1 前 16 位>`，不包含令牌、口令等敏感信息；值统一 JSON 序列化。
- 失效使用 `SCAN` 前缀遍历后批量删除，不使用 `KEYS`，避免大键空间阻塞（`backend/app/cache.py:223-241`）。
- 异常一律降级直连数据库，接口不因缓存故障返回 500；故障告警进程内只输出一次，避免日志放大（`backend/app/cache.py:64-104`）。

## 六、数据安全与开放接口

### 6.1 数据分级与最小授权

| 数据类别 | 分级 | 访问控制 |
| --- | --- | --- |
| 价格与特征明细、预测结果 | 内部 | 登录 + 对应 `*:view` 权限；导出另需 `monitor:export` |
| 预警记录与处置意见 | 内部 | `alert:view` 查看，`alert:handle` 处置 |
| 账号、角色、审计日志、运行日志 | 敏感 | 仅 `admin:user` / `admin:role` / `admin:audit` |
| 开放 API 密钥、SMTP 凭据、数据库口令 | 敏感 | 仅服务端配置与管理员接口；密钥列表返回掩码 |
| 报告与模型产物 | 内部 | `report:view` / `forecast:view`；对象存储私有桶 |

### 6.2 数据导入与上传校验

- 仅接受 `.csv` / `.txt` 后缀，其他类型返回 `E4001`（`backend/app/routers/data_gov.py:337-339`）。
- 单文件上限 20 MB（`backend/app/services/ingest.py:25`），超限直接拒绝。
- 逐行校验日期格式、品种/地区/市场存在性、价格数值范围（1～100000 元/公斤），错误明细最多保留 200 条、质量问题最多 200 条，避免异常文件撑爆响应与库表。
- 导入结果写「导入」审计与「数据导入完成」通知；导入成功后自动失效驾驶舱、价格、字典缓存。

### 6.3 日志与输出脱敏

- 访问日志只记录方法、路径、状态码、耗时、缓存状态，不记录请求体、响应体、令牌与口令。
- 审计详情截断至 250 字符；结构化日志单字段截断至 512 字符。
- 开放 API 调用方密钥在列表与详情中掩码为「前 6 位 + ****」，完整密钥仅在创建与轮换的响应中返回一次。

### 6.4 开放 API 安全

- 双鉴权：`Authorization: Bearer <JWT>` 或 `X-Api-Key: <client_key>`；密钥不存在或已停用统一返回 401 `E4010`「开放 API 密钥无效或已停用」（`backend/app/services/open_api_gate.py:100-119`）。
- 限流：按调用方 `rate_limit`（次/分钟，默认 60，可在 1～600 间配置）计数；优先 Redis `INCR + EXPIRE`，Redis 故障时降级为进程内计数（`backend/app/services/open_api_gate.py:49-95`）；超限返回 429 `E4290`「调用频率超出限制，请稍后重试」。实测：限额 60 的调用方正常返回 200，临时限额 2 的调用方第 3 次请求返回 429；Redis 指向错误端口时同样在内存降级下返回 429。
- 流水与追溯：每次已鉴权调用写 `open_api_call`（路径、方法、状态码、耗时），累计调用方 `call_count` / `last_call_at`，并在写入时清理超过 7 天的历史流水（`OPEN_API_CALL_RETENTION_DAYS`）。
- 密钥治理：创建、修改、轮换、删除均写审计；轮换同时更换 `client_key` 与 `secret`；停用即时生效。
- 用量查询：`GET /api/open-clients/{id}/usage?days=7` 返回按日调用量、平均耗时、错误率与前 5 路径，权限 `data:view`。

## 七、合规差距与整改计划

对照等级保护基本要求的三级条款做差距比对，当前系统在企业内网单机场景可满足基础要求，尚存 5 项差距：

| 序号 | 差距项 | 风险说明 | 优先级 | 工作量估算 | 整改方案 |
| --- | --- | --- | --- | --- | --- |
| 1 | 传输层未启用 TLS | 内网明文传输，令牌与业务数据可被链路嗅探 | 高 | 1 人日 | 前置 Nginx 终结 TLS，配置证书、HSTS、TLS 1.2+，后端仅监听回环 |
| 2 | 未做等级保护测评与备案 | 无法出具合规证明，责任边界不清晰 | 高 | 外部 2～4 周 | 按二级/三级定级备案，委托测评机构测评并整改 |
| 3 | 未启用双因子认证 | 口令泄露即可登录，管理账号风险最高 | 中 | 3 人日 | 管理账号接入 TOTP，登录流程增加动态码校验与审计 |
| 4 | 权限点为基础 RBAC，缺字段级/行级控制 | 同角色内可见全量字段与全量地区数据 | 中 | 3 人日 | 在 `role_permission` 之外增加数据范围表，查询层注入地区/字段过滤 |
| 5 | 密钥与口令分散在配置文件与环境变量 | 轮换与审计困难，易随备份泄露 | 中 | 1 人日 | 接入密钥托管（如 Vault 或云 KMS），启动时注入，禁止明文落盘 |

补充待改进项（不列入上表优先级但已识别）：登录失败次数锁定与验证码、口令复杂度策略（当前仅最小 8 位）、审计日志异地归档与完整性校验、备份文件加密。

### 7.1 结论

平台在应用层已实现「口令散列存储、令牌即时注销、RBAC 最小授权、全链路审计、缓存降级、开放接口限流与密钥治理」六项核心能力，越权与注销场景有可复跑的接口门禁断言作为证据；对外服务前应优先完成 TLS 与等级保护测评两项高优先级整改。
